## 1. Product summary

A multi-church PWA for managing church youth "services" (خدمات): classes, servants (خدام), served kids (مخدومين), points, competitions, visitation (افتقاد), and servant preparation (تحضير).

Hierarchy (each level only sees and manages what's below it):

```
Super Admin (platform owner)
└── Church (كنيسة)            ← managed by Church Admin(s)
    └── Service (خدمة)        ← managed by Service Admin(s)
        └── Class (فصل)       ← defined by Service Admin
            ├── Servants (خدام)
            └── Served (مخدومين)
```

One user account can hold different roles in different places (e.g. servant in service A and service admin in service B). **Roles live on membership rows, never on the user/profile.**

## 2. Tech stack

- **Next.js (App Router) + TypeScript** — strict mode
- **Tailwind CSS + shadcn/ui** — RTL-first, mobile-first
- **Supabase** — Auth (email/phone + password), Postgres, Row Level Security, Storage
- **PWA** — installable, manifest + service worker (use `serwist` or `@ducanh2912/next-pwa`)
- **QR** — generate with `qrcode`; scan with `@yudiel/react-qr-scanner` (camera) plus a manual code-entry fallback
- **Deploy** — Vercel (frontend) + Supabase cloud
- Arabic font: `IBM Plex Sans Arabic` or `Cairo` via `next/font`
- `<html lang="ar" dir="rtl">` everywhere. Use logical CSS (`ps-`, `pe-`, `ms-`, `me-`), never `pl-`/`pr-`.

## 3. Roles & permissions

| Role | Scope | Can do |
|---|---|---|
| `super_admin` | Platform | Create/edit/delete churches. Pick any existing user as Church Admin. |
| `church_admin` | One church | Create services in their church. Add servants to one **or more** services. Appoint Service Admins. View all servants in the church. |
| `service_admin` | One service | Everything inside their service only: create/edit classes; assign servants to classes; assign served kids to servants for visitation; generate join QR codes; create competitions; publish posts (timeline); manage gifts & redemptions; view/adjust points; track visitation and servant preparation attendance; view all servants and served in the service. |
| `servant` | One service (can be in several) | See own points and rank among servants. See the served kids assigned to them. Log visits (افتقاد). Check in to preparation sessions (تحضير). View their class. |
| `served` | One service + one class | Home (points, avatar, timeline), competitions, achievements, leaderboards. |

Rules:
- A Service Admin has **no** access to other services, even in the same church.
- A Church Admin has no access to other churches.
- Every permission must be enforced by **RLS in Postgres**, not only in the UI.

## 4. Key flows

### 4.1 Served kid joins (QR)
1. Kid creates an account (name, phone, password, optional avatar).
2. Kid scans a QR code (or types the code) → `/join?code=XXXX`.
3. RPC `join_with_code(code)` validates the code (active, not expired) and creates a `service_members` row with `role = 'served'`, `class_id` from the code, `status = 'active'`.
4. Redirect to the served home page.

**Assumption (confirm with owner):** one QR code per **class**, generated by the Service Admin. Codes can be regenerated/deactivated and can have an expiry date. Also support a service-level code where `class_id` is null → member joins with `status = 'pending'` until the Service Admin assigns a class.

### 4.2 Servant added
1. Church Admin picks an existing user and adds them as `servant` to one or more services in the church.
2. Service Admin assigns them to a class and assigns served kids to them for visitation.

### 4.3 Points
- Points are an **append-only ledger** (`points_ledger`). Never store a mutable balance.
- Every entry has `service_id`, `class_id`, `user_id`, `points` (can be negative), `reason`, optional `source_id`.
- Leaderboards:
  - **Service level:** sum per user over the service.
  - **Class level:** sum per user filtered by `class_id`.
  - Separate leaderboards for servants and for served.
- Corrections = a new reversing entry, not edits/deletes.
- Default point values per reason are configurable per service (`point_rules`).

Sources of points:
- Served: competition result, attendance (future), manual award by Service Admin, gift redemption (negative).
- Servant: logging a visit, attending a preparation session, manual award.

## 5. Database schema (Supabase / Postgres)

Use UUID PKs, `created_at timestamptz default now()` on all tables. Write as SQL migrations in `supabase/migrations/`.

```sql
-- enums
create type member_role as enum ('service_admin','servant','served');
create type member_status as enum ('pending','active','removed');
create type church_role as enum ('church_admin','servant');
create type point_reason as enum ('competition','visit','preparation','attendance','manual','gift_redemption','achievement');
create type visit_type as enum ('home','call','message','other');

profiles(id uuid pk references auth.users, full_name text, phone text, avatar_url text, is_super_admin bool default false)

churches(id, name, address, created_by)
church_roles(id, church_id, user_id, role church_role, unique(church_id,user_id,role))

services(id, church_id, name, description, logo_url)
classes(id, service_id, name, sort_order)
service_members(id, service_id, user_id, role member_role, class_id null, status member_status,
                unique(service_id,user_id,role))

join_codes(id, service_id, class_id null, code text unique, is_active bool, expires_at null, created_by)

servant_assignments(id, service_id, servant_id, served_id, unique(service_id, served_id))  -- who visits whom

visits(id, service_id, servant_id, served_id, visit_type, visited_at, notes)

prep_sessions(id, service_id, title, session_date)
prep_attendance(id, session_id, servant_id, checked_in_at, unique(session_id,servant_id))

point_rules(service_id, reason point_reason, points int, primary key(service_id, reason))
points_ledger(id, service_id, class_id null, user_id, points int, reason point_reason, source_id uuid null, note text, created_by)

posts(id, service_id, class_id null, author_id, body text, image_url, created_at)   -- class_id null = whole service

competitions(id, service_id, class_id null, title, description, starts_at, ends_at, max_points int, is_published bool)
competition_questions(id, competition_id, question text, options jsonb, correct_index int, points int, sort_order)
competition_entries(id, competition_id, user_id, answers jsonb, score int, submitted_at, unique(competition_id,user_id))

gifts(id, service_id, name, image_url, cost_points int, stock int null, is_active bool)
gift_redemptions(id, gift_id, user_id, status text check (status in ('requested','approved','delivered','rejected')))

achievements(id, service_id, name, description, icon, criteria jsonb)   -- e.g. {"type":"points_total","gte":500}
user_achievements(id, achievement_id, user_id, earned_at, unique(achievement_id,user_id))
```

Views:
- `v_service_leaderboard(service_id, user_id, role, total_points, rank)`
- `v_class_leaderboard(service_id, class_id, user_id, role, total_points, rank)`

### 5.1 RLS helper functions (security definer, stable)
- `is_super_admin()`
- `is_church_admin(church_id)`
- `is_service_admin(service_id)` — true if service_admin of the service **or** church_admin of its church **or** super_admin
- `is_service_member(service_id)` — any active role in the service
- `is_assigned_servant(served_id, service_id)`

Write RLS policies on **every** table using these. Default deny.

### 5.2 RPCs (security definer, validate permissions inside)
- `join_with_code(p_code text)`
- `award_points(p_service, p_user, p_points, p_reason, p_note)` — service admin only
- `log_visit(p_service, p_served, p_type, p_notes)` — assigned servant only; inserts visit + ledger entry from `point_rules`
- `check_in_prep(p_session)` — servant of that service; inserts attendance + ledger entry
- `submit_competition(p_competition, p_answers jsonb)` — grades server-side, inserts entry + ledger
- `redeem_gift(p_gift)` — checks balance ≥ cost, creates request; ledger debit on approval
- `regenerate_join_code(p_code_id)`

Never let the client insert into `points_ledger` directly. Never send `correct_index` to served users.

### 5.3 Storage
- Bucket `avatars` (private, signed URLs), bucket `service-media` for posts/gifts/logos.
- Served users are mostly minors: keep personal data minimal, no public profiles, nothing visible outside their own service.

## 6. Screens / routes

### Auth
- `/login`, `/signup`, `/join?code=` (also handles not-logged-in → signup → back to join), `/scan`
- After login: if the user has multiple memberships, show a "اختار الخدمة" picker; remember last choice.

### Super Admin — `/admin`
- Churches list + create/edit
- Church detail: assign/remove Church Admins (search existing users by name/phone)

### Church Admin — `/church/[churchId]`
- Services list + create
- Servants pool: add an existing user as servant to one or more services
- Appoint/remove Service Admins per service

### Service Admin — `/s/[serviceId]/manage`
- Dashboard: counts, top points, pending members, recent visits
- الفصول: CRUD classes
- الأعضاء: servants & served, move between classes, approve pending, remove
- أكواد الانضمام: generate QR per class, download/print QR, deactivate
- الافتقاد: assign served → servants; visits log with filters; who hasn't been visited in N days
- التحضير: create prep sessions, view attendance
- النقاط: ledger, manual award, point rules settings
- المسابقات: create competition with questions, publish, see results
- البوستات: timeline posts
- الهدايا: gift catalog, redemption requests
- الإنجازات: define achievements

### Servant — `/s/[serviceId]/servant`
- Home: my points, rank among servants, upcoming prep session
- مخدوميني: assigned served list with last-visit date + "سجل افتقاد" button
- التحضير: check in
- الترتيب: servants leaderboard (service + class)

### Served — `/s/[serviceId]/home` (bottom nav, 3 tabs)
1. **الرئيسية:** avatar, name, total points (service + class), timeline of posts
2. **المسابقات:** available competitions → take quiz → result
3. **الإنجازات والترتيب:** earned/locked achievements, leaderboard toggle (الخدمة / الفصل)

## 7. Conventions

- Folder structure: `app/(auth)`, `app/admin`, `app/church/[churchId]`, `app/s/[serviceId]/(manage|servant|home)`, `lib/supabase` (server + browser clients), `components/ui` (shadcn), `components/*` feature components.
- Generate Supabase types (`supabase gen types typescript`) into `lib/database.types.ts`.
- Server Components + Server Actions for data; route guards in `middleware.ts` + per-layout role checks.
- All user-facing strings in Arabic; keep them in `lib/strings.ts` so they're easy to edit.
- Dates in Africa/Cairo timezone, Arabic locale formatting.
- Seed script with: 1 super admin, 1 church, 1 service, 2 classes, 2 servants, 6 served, sample points, 1 competition.
- Tests: SQL tests for RLS (each role can/can't read/write what it should), plus Playwright smoke test for the join-by-QR flow.

## 8. Build phases (stop and report after each)

1. **Setup:** Next.js + Tailwind + shadcn + RTL + font + PWA manifest; Supabase project, auth, profiles.
2. **Schema + RLS:** all migrations, helper functions, policies, RLS tests, seed data.

5. **Points:** ledger, rules, RPCs, leaderboards (service + class).
6. **Servant interface:** assignments, visits, prep check-in, servant leaderboard.
7. **Served interface:** home + timeline, competitions, achievements & ranking.
8. **Extras:** gifts & redemptions, achievements engine, posts with images, polish, deploy to Vercel.
